# VideoBrowser 1.11.6 – Stage 3.6 (xHamster frame extraction and diagnostics)

- Version Name: `1.11.6`
- Version Code: `20`
- الهدف: معالجة تقرير xHamster الذي أظهر Blob/MSE مع صفر إعدادات مشغّل/مصادر، وتحسين تشخيص صيغ HLS التي يرفضها فلتر المدة.

## ما تغير

1. قراءة بنية المشغّل المعلنة `initials.videoModel.sources` و`initials.xplayerSettings.sources` في الصفحة الرئيسية والإطارات التي تحتوي الفيديو.
2. التقاط روابط HTTP(S) الواضحة فقط، مع الاحتفاظ ببيانات الجودة/الترميز/الدقة عندما تكون معلنة داخل بنية المشغّل.
3. تجاهل مفاتيح download والإعلانات والمعاينات. القيم المعتمة/المشفرة تُحصى للتشخيص فقط ولا يتم فكها أو تحويلها.
4. تمرير عدد مصادر xHamster والجودات المعلنة والقيم المعتمة من iframe إلى التشخيص الأصلي.
5. منع عرض مصادر xHamster المعلنة أثناء preroll المصنّف، ثم استعادتها عند انتقال عنصر الفيديو إلى المحتوى.
6. تجاهل قوائم Resource Timing التي سبق تحميلها قبل حد الانتقال من الإعلان إلى المحتوى داخل iframe، مع السماح بالقوائم الحديثة التي تُحمّل بعد الانتقال.
7. عند رفض Content Filter لصيغة بسبب اختلاف المدة، يُظهر التشخيص المضيف ومصدر الالتقاط والمدة المكتشفة مقابل مدة المشغّل بدل الاكتفاء بعدّاد الرفض.

## حدود معروفة

- لا يتم فك قيم `xplayerSettings` المعتمة أو محاولة تحويلها إلى روابط. إذا لم يعرض الموقع رابطًا واضحًا أو قائمة HLS/DASH يمكن قراءتها، سيظل المصدر غير قابل للاستخدام في هذه المرحلة.
- لا نرفع الجودة اصطناعيًا إلى 2K/4K. تظهر هذه الدقة فقط إذا كشفت بيانات المشغّل أو القائمة عن تمثيل حقيقي بهذه الدقة.
- لا يثبت اختبار المصدر أن كل فيديو في xHamster يوفّر 2K؛ ذلك يعتمد على تمثيلات كل فيديو وما يسمح الموقع بعرضه في الجلسة.
- لم يُنفذ Android `assembleDebug` في بيئة إعداد الحزمة لعدم توفر Android SDK/Gradle. يلزم تأكيد البناء عبر GitHub Actions قبل التثبيت.

## الاختبارات المحلية المنفذة

- 11 اختبار JavaScript: التقاط المصادر، API/JSON، HLS، جودة player config، document-start، iframe، Shadow DOM، preroll، invariants، واستخراج xHamster في الصفحة الرئيسية والإطار.
- 5 مجموعات Kotlin: HLS master، resolver، metadata، capture headers، signed URL expiry.
- اختبار NetProbe fallback: Range 410 ثم GET header-only، مع بقاء 410 الحقيقي مرفوضًا.
- تحقق من تجميع `ApiCaptureScript.kt` عبر Kotlin compiler.
- لم يتغير `DownloadCenter.kt` أو `Hls.kt` عن المصدر 1.11.5.1.

تفاصيل تشغيل الاختبارات: `tools/quality-tests/README_AR.md`.

# VideoBrowser 1.11.5 – Stage 3.5

تصحيح مرحلة فحص مصادر المشغل التي عادت HTTP 410.

- التقاط سياق الطلبات ذات الروابط غير النمطية التي أعلنها المشغل صراحة، دون تحويل نقاط API العامة إلى صيغ تنزيل.
- ربط ترويسات الطلب الآمنة بالرابط المطابق حرفيًا فقط، مع التحقق من حداثة السياق وأصل إطار الفيديو.
- عدم إعادة استخدام سياق طلب تم التقاطه أثناء الإعلان لتمثيل المحتوى بعد الانتقال.
- عند رفض CDN لفحص Range، يجرب التطبيق HEAD ثم GET دون Range لقراءة ترويسات الاستجابة فقط؛ لا ينزل جسم الفيديو أثناء الفحص.
- إذا أعاد الخادم 410 حتى مع الطلب العادي، يبقى المصدر مرفوضًا ويظهر التشخيص أن الرابط غير متاح حتى بعد فحص Range/HEAD/GET. لا يحاول التطبيق توليد رابط أو تخطي انتهاء صلاحيته.

لم يتغير DownloadCenter.kt أو Hls.kt عن الإصدار 1.11.3.

شغّل اختبارات JavaScript وKotlin المذكورة في `tools/quality-tests/README_AR.md`. يتطلب بناء APK النهائي Android SDK وGradle، ثم اختبارًا على الجهاز للتأكد من أن سياقات الطلب الفعلية ترتبط بروابط player-flashvars.

- حصر Resolver أثناء الإعلان على مصادر المشغل المعلنة صراحة، مع الاستفادة من مدة المحتوى التي كشفها المشغل للتحقق من أن الصيغ تخص الفيلم.
- إصلاح التخزين السلبي لنتيجة صفر صيغ: الضغط اليدوي مرة أخرى يسمح بإعادة تحليل مصادر WebView وإعادة محاولة yt-dlp، بدل تكرار رسالة الفشل دون محاولة جديدة.
- تم تحديث اختبارات الصفحة الرئيسية وiframe وxHamster لتتأكد من ظهور صيغ المحتوى أثناء الإعلان، مع بقاء روابط الإعلان وبيانات المقاطع القديمة مستبعدة.

هذه التعديلات تصلح منطق الالتقاط وإعادة المحاولة في المصدر، لكنها لا تثبت أن كل رابط CDN سيقبل الطلب؛ أخطاء HTTP 410 أو رفض الجلسة يجب تأكيدها على الجهاز بعد البناء.

## محرك yt-dlp — التنفيذ السابق (أصبح مستبدلًا)

كان الإصدار السابق يستخدم `youtubedl-android:0.18.1` وبيئة Python 3.8. هذه البيئة لا تتضمن محرك `curl_cffi` الحديث اللازم لمحاكاة TLS في بعض المواقع؛ لذلك لم تكن مناسبة لمعالجة أخطاء Pornhub من نوع HTTP 410. استبدل هذا التنفيذ في 1.12.0، ولا ينبغي استخدام تعليمات تحديث المحرك القديمة معه.

### بناء APK التجريبي

يتضمن المصدر GitHub Actions workflow باسم `Build APK`. كانت هذه خطوات تاريخية للإصدار 1.12.1–1.12.2؛ في الإصدار 1.12.3 وما بعده أصبح البناء ينتج APK واحدًا، راجع قسم الإصدار الحالي في بداية الملف. الحزمة المصدرية هنا ليست APK مبنيًا؛ لم يُنفذ Android/Gradle assemble في بيئة إعدادها لعدم توفر Android SDK وGradle.

### ترخيص مكون الطرف الثالث

## v1.11.9 — تحسين سياق طلبات Pornhub

- ترويسات Pornhub الأساسية تستخدم Referer الجذر وOrigin للمضيف الذي فتح صفحة الفيديو، وفق نمط الإصلاح المدمج في مستخرج yt-dlp الرسمي.
- إذا طلب WebView جودة واحدة فقط، يمكن مشاركة الترويسات الآمنة (User-Agent وReferer وOrigin وAccept وAccept-Language) مع روابط الجودات الأخرى على مضيف CDN نفسه، بشرط مطابقة أصل صفحة المشغل وحداثة الطلب.
- لا تتم مشاركة Cookie أو Authorization أو أي ترويسة مخصصة؛ يقرأ التطبيق Cookie من CookieManager لكل رابط على حدة.
- أضيف إلى التشخيص عدد الجودات التي ورثت سياق WebView من المضيف نفسه.
- هذا تحسين لتمرير سياق طلب المتصفح، وليس بديلًا عن TLS browser impersonation. إذا استمر HTTP 410 من Pornhub بعده، فيلزم دعم curl_cffi/محاكاة TLS أو طبقة شبكة متوافقة؛ لا نعتبر 410 دليل انتهاء الرابط وحده.


## الإصدار 1.12.0 — استقرار جودات Pornhub

- يطلب yt-dlp كل صيغ الصفحة بدل الاعتماد على الجودة المحددة حاليًا داخل المشغل فقط.
- لا يُسقط خيارات الجودة المختلفة لمجرد اشتراكها في رابط manifest واحد؛ يحتفظ بمعرّف `format_id` لكل تمثيل.
- عند تنزيل خيار yt-dlp، يعاد استخراج الصفحة واختيار معرّف الصيغة نفسه باستخدام Python/curl_cffi مع Chrome impersonation، بدل فحص URL عبر HttpURLConnection.
- إزالة User-Agent الخاص بـWebView عند محاكاة Chrome كي لا يحدث تعارض بين بصمة TLS وبصمة المتصفح المعلنة.
- تنزيل الملفات الطويلة لا يُنهى بعد ست دقائق؛ مهلة المحرك تصل إلى أربع ساعات مع إمكانية الإيقاف من واجهة التطبيق.

## الإصدار 1.12.0 — محرك Python/curl_cffi موحد للاستخراج والتنزيل

- استبدال بيئة Python 3.8 القديمة ببيئة Android ARM64 مبنية على Python 3.14.8 وتضم `curl_cffi 0.17.0`.
- استخدام إصدار yt-dlp المستقر `2026.10.26` كحزمة Python zipapp، مع فحص SHA-256 للملفات التي تُنزّل وقت البناء.
- في صفحات Pornhub يستخدم المحرك `--impersonate chrome` مع `Origin` و`Referer` ملائمين لصفحة الموقع.
- أصبحت Cookies تؤخذ عند الطلب من Android CookieManager وتوضع مؤقتًا في ملف Netscape محدود بمضيف صفحة الفيديو، ثم يُحذف الملف بعد الاستخراج/التنزيل. لا تُمرر Cookies كـ`--add-headers` ولا تحفظ في ملف مهام التنزيل.
- كل صيغة مستخرجة بواسطة yt-dlp تحتفظ بعنوان الصفحة ومعرّف الصيغة. عند تنزيلها يعاد تشغيل yt-dlp على الصفحة نفسها وبمعرّف الصيغة نفسه؛ بذلك يستخدم التنزيل `curl_cffi` أيضًا بدل الرجوع إلى `HttpURLConnection` الذي أعاد 410.
- صيغ WebView التي لم تأتِ من yt-dlp تستمر عبر مسار التنزيل الأصلي.
- يدعم مسار yt-dlp الآن صيغ DASH المدمجة، كما يجمع صيغة الفيديو المنفصلة مع أفضل مسار صوتي متاح باستخدام محدد `videoId+audioId`. لا تزال قوائم MPD التي لا يستطيع yt-dlp ربطها بصفحة الفيديو غير قابلة للتنزيل عبر Resolver المباشر.

### إعداد ملفات البناء

في 1.12.3 ينفذ `tools/prepare_android_runtime.sh` تنزيل Runtime Python ARM64 وملف yt-dlp الرسمي ويتحقق من SHA-256. توضع ملفات Python التنفيذية في `app/src/main/jniLibs/arm64-v8a` داخل APK الرئيسي، بينما يوضع yt-dlp في `app/src/main/assets/yt-dlp`. تنفذ GitHub Actions هذا الإجراء تلقائيًا ثم تبني `:app:assembleDebug` فقط. يجب أن يتوفر اتصال إنترنت أثناء البناء.

هذه الحزمة Source ZIP وليست APK. كما أن دعم `curl_cffi` في هذه النسخة محصور في ABI `arm64-v8a`.

### حدود ما تم إثباته

اختبارات المصدر تتحقق من ربط محرك الاستخراج بمحرك التنزيل، ومن طلب Chrome impersonation وملف Cookies المؤقت. لكنها لا تثبت أن كل فيديو في Pornhub سيعمل أو أن كل روابط CDN لن تعيد 410؛ يلزم بناء APK واختباره على جهاز Android فعلي. إذا فشل yt-dlp نفسه بعد المحاكاة، قد تكون الجلسة أو الرابط أو قيود الموقع هي السبب.
